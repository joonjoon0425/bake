# native / burn representations (35-refactor)

20261107

## Summary

- **`Native`** represents a single environment's values. But note that `ndarray` types still always have size 1 along the dim 0, due to unification with `burn` tensors.
- **`Burn`** represents a vectorized environment values. For example, vector environments transition and minibatches...
- Non-vector environment will only be dealt with `Native` values. Vectorized and all other batch-related values will be dealt with `Burn` values.

## Background

Until 34-refactor-v5, tabular was also using `burn`, since I tried to unify the tabular and deep RL algorithms to use same structs and traits. But the wall-clock time got really slow for tabular algorithms. So I splited data types into two categories, `burn` and without `burn`. Note that 34-refactor-v4 also tried to do this but failed, since I was made too much abstraction. This time I don't to that.

## 1. `native` and `burn`

- **Native**
    - does not uses `burn` type.
    - no `Device`.
    - one value -> one environment
    - n-dimensional array type (`ArrayD`) will always have size 1 at dim 0, for matching shape with `burn`. It is not for batch dimension.
- **Burn**
    - uses `burn` library and types
    - uses `Device`
    - all batch-related operations happens here.
- **no batch for `native`**
    - allowing this will create anthoer representation of `DiscreteSpace`'s `Native` batch version and it is confusing since there is already `Burn` DiscreteSpace, which is for vector environments.

## 2. name and stucture

- at `crate::core`, we have empty marker struct `pub struct Native` and `pub struct Burn`. I won't put any member variable.
- for each concepts, there exists a trait.
    - for example, action selection (greedy, epsilon-greedy, ...) is a concept, and there exists several ways to implement it.
    - here, the implementations are `Native` and `Burn`, so I use a single struct with generics bounded with trait `ActionSelectorRepr`.
    - the marker struct `Native` and `Burn` will implement this. The data other than common values such as epsilon will be indicated by the `ActionSelectorRepr`'s associated type `Inner`, and it allows different values among same-name (actually there is a generic) structs.

  | concept | trait | Native | Burn |
  |---|---|---|---|
  | action selection | `ActionSelectorRepr { type Inner }` | `SmallRng` | `()` |
  | discrete space | `DiscreteSpaceRepr { type Inner }` | `SmallRng` | `Device` |
  | continuous space | `ContinuousSpaceRepr { type Bound<D>; type Inner }` | `ArrayD<f32>`, `SmallRng` | `Tensor<D>`, `Device` |

- struct representing one concept has generic markers, which show the implementation: `EpsGreedy<Repr>`, `DiscreteSpace<Repr>`, `ContinuousSpace<Repr, D>`.
- the constructors will be in each implementations impl block, with lower cased name `native` and `burn`, like `X::native(...)` and `X::burn(...)`.
- the user then selects the concept, (`EpsGreedy`) and choose the implementation next (`EpsGreedy::native` or `EpsGreedy::burn`).

## 3. trait

- there also exists traits separating the implementation, if a single trait is difficult to contain two implementations at once
    - If the function signatures are not compatible.
        - `NativeSpace` / `BurnSpace` has different `sample` signature
        - `NativeDiscreteActionSelector` / `BurnDiscreteActionSelector` uses two different discrete constraint trait bounds. See below.
        - `NativeDiscreteConstraint` / `BurnDiscreteConstraint`. Note that the constraint cannot be made into a single trait with associated types, since then `()` will be only usable for one representation, `Native` or `Burn.
- `Environment` and `VectorEnvironment` are bounded by the traits
    - `Environment`: `ObsSpace: NativeSpace`, `ActionSpace: NativeSpace`
    - `VectorEnvironment`: `ObsSpace: BurnSpace`, `ActionSpace: BurnSpace`, `Constraint: BatchOps`, `Reward: BatchOps`
- There exists two traits, but the user still sees one concept struct and selects the implementation.

## 4. environments

1. **vector environments are only made with `burn`.**
2. **single environments are only made with `native`.** for now, single burn environment is not allowed.
    - `Environment` has its `Space` bounded with trait `NativeSpace`.
    - If GPU environment or differentiable environment is required, implement it with `VectorEnvironment` (n=1 is possible)
3. single → vector environment conversion is done with `SynchronizedVectorEnvironment`(SyncEnv).
    - That is, even if you had written your environment with `Native` representation, you can use it as `Burn` representation.
    - bound: `E: Environment<ObsSpace: ToBurnSpace, ActionSpace: ToBurnSpace, Constraint: ToBurn, Reward: ToBurn>`
4. **deep rl algorithms will only run on vector environments.**
    - But as I wrote in 3, single environments can always be transformed into vector environment (if the bounds are satisfied) with `SynchronizedVectorEnvironment` wrapper 
5. There will be two separated pair of wrapper for environment and vector environment.
   - for non-vector: `core::env::wrapper`.
   - for vector: `core::env::wrapper::vec` with same wrapper name. 예: `RecordEpisodeStatistics`, `OneHotObservation`.

## 5. 공간 (Space)

- `DiscreteSpace`
  - Native: 원소 `usize`, `SmallRng`를 가진다.
  - Burn: 원소 텐서, `Device`를 가진다.
- `ContinuousSpace<Repr, D>`
  - D는 앞축을 포함한 rank다 (특징 rank + 1). burn `Tensor`의 rank가 고정이라서 이렇게 정했고, native도 통일을 위해 같은 규칙을 따른다.
  - shape, low, high는 모두 앞축을 포함한다. 예: `[1, 4]`.
  - Native: 원소와 bounds가 `ArrayD<f32>`, device가 없다.
  - Burn: 원소와 bounds가 `Tensor<D>`, `Device`.
- `ByteSpace<Repr, D>`도 같은 구조다. 원소는 u8이다.
- native에 ndarray를 쓰는 이유:
  - 이미 의존성에 있다 (`ndarray = "0.17.2"`).
  - numpy 0.29와 같은 ndarray 버전이라 gym 값을 그대로 받을 수 있다.
  - `Vec<f32>`와 달리 shape이 보존된다.
- `ArrayD`를 고른 이유: ndarray의 `Dimension`은 N마다 따로 구현되어 있어서, const 제네릭 D로 `Array<f32, Dim<[Ix; D]>>`를 쓰면 바운드가 붙는다.
- gym과 주고받을 때 앞축을 붙이고 뗀다.
  - Python → Rust: `insert_axis(Axis(0))`
  - Rust → Python: 앞축을 제거한다.

## 6. convert

- the conversion between `Native` and `Burn` will only happen at the `SynchronizedVectorEnvironment` wrapper

  | converted object | trait | function | direction |
  |---|---|---|---|
  | observation space and action space | `ToBurnSpace` | `into_burn(self, device) -> BurnSpace` | native → burn |
  | observation | `ToBurnSpace` | `bind(Vec<원소>, device) -> burn 원소` | native → burn |
  | action | `ToBurnSpace` | `unbind(burn 원소) -> Vec<원소>` (안에서 `into_data` 한 번) | burn → native |
  | reward, constraint | `ToBurn` | `bind(Vec<Self>, device) -> BurnElem` | native → burn만 |
  | boolean flag | `ToBurn for bool` | `Tensor<1, Bool>` | native → burn |

- `bind` binds the element vector into one `Burn`, batched element with batch shape [vector length].
- `unbind` splits the element along the first batch dimension.
- the reward and constraint has no space for conversion, so it implements `ToBurn` trait, which only requires `into_burn`.
    - the length comes from `Vec`. No worries for `()`.
    - implementations: `()`, `bool`, `f32`, `usize`, `[bool; N]`, `Vec<bool>`
- conversion first vs binding, unbinding first: benchmark by claude (burn 0.23.0-pre.1, `flex` CPU, 2 core, repeat 2000 mean).

  | N | obs: elementwise conversion + `cat` | obs: bind first, convert later | action: unbind first, elementwise `into_scalar` converion | action: `into_data` convert first, unbind later |
  |---|---|---|---|---|
  | 8 | 3.3 µs | 0.4 µs | 5.6–6.8 µs | 0.2–0.3 µs |
  | 64 | 22–30 µs | 0.9–1.0 µs | 41–44 µs | 0.3 µs |
  | 256 | 94–96 µs | 2.1 µs | 166–177 µs | 0.7 µs |

## 7. Tape와 Transition

- `Tape<E: Environment>`
  - for single `Native` environments. Outputs `Transition<Native, ..>`. tabular and on-line linear uses it.
  - no autoreset.
- `VectorTape<E: VectorEnvironment>`
  - outputs `Batch<Transition<Burn, ..>>`. deep rl uses this tape.
  - `autoreset` possible optionally.

## 8. linear

- on-line (single env, one step): `Native`
- batch (vector env, minibatch): `Burn`

## 9. gymnasium

- single gym environment: `Native` (`NativeGymSpace`).
- currently for deep, wrap it with SyncEnv.
- later when required, gymnasium environments will be implemented with `VectorEnvironment`.
    - set autoreset as `DISABLED` and `reset(options={"reset_mask": ...})` will be connected to `VectorTape`'s reset mask.
    - reference: https://gymnasium.farama.org/main/api/vector/autoreset/

## 10. buffer

- 사용처가 deep뿐이라 `core`에서 `deep`으로 옮긴다.
- Buffer = Storage + Sampler.
  - 생성자: `Buffer::replay`, `Buffer::prioritized_replay`, `Buffer::rollout`, `Buffer::episode`.
  - 별칭: `ReplayBuffer<T>` 등. `T: BatchOps` 제네릭 하나만 둔다.
- Ring 저장소는 time-major `[capacity_steps, N]`로 둔다. 이러면 용량을 N으로 나눠떨어지게 맞출 필요가 없다.
- Rollout도 샘플러를 둔다.
  - 버퍼에 추가적인 내용물을 넣을 수 있는 함수를 작성해서 PPO에도 적용 가능하게 한다.
  - 나중에 샘플 방식을 바꾸더라도 `Batch`에 구현하는 게 아니라 `Sampler`를 새로 만들기만 하면 된다.
  - 다만 사용자가 롤아웃 업데이트 후 직접 clear를 호출해야 한다. 
- Episode는 늘어나는 저장소로 둔다. 예전 RolloutBuffer의 쌓기 방식을 재사용한다.
- Sampler는 인덱스와 가중치를 돌려준다.
- 샘플 정보(`is_weights`, `indices: Tensor<1, Int>`)는 샘플된 Batch의 `BatchDict`에 typed `Key<T>` 상수로 넣는다. 그래서 알고리즘 시그니처에 `SampleInfo`가 따로 없다.
- n-step 윈도우는 저장소가 만든다. 할인과 off-policy importance sampling은 알고리즘 쪽에서 한다.
- sum tree와 PER은 논문을 보고 직접 다시 구현한다. v5의 `prioritized.rs`를 검증용 기준으로 남긴다.
- 아직 구현 전이다. 지금 `deep/buffer`는 예전 구조다.
