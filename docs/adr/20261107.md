# native / burn 표현 분리 (35-refactor)

20261107

## 배경

v5까지는 tabular도 burn에 의존하게 해서 모듈을 하나로 합쳤지만, tabular가 너무 느려졌다 (`tabular.txt` 참고).
그래서 표현을 native와 burn으로 나누고, 각 개념마다 구현을 두 벌 두기로 했다.
v4의 `Repr`는 모든 개념이 공유하는 전역 타입 패밀리를 만들려다 실패했다. 이번에는 그렇게 일반화하지 않는다.

## 1. native와 burn의 정의

- **Native**
  - burn 타입을 쓰지 않는다 (std 타입과 ndarray).
  - device가 없다.
  - 값 하나는 단일 환경의 한 시점이고, 배치 축이 없다.
- **Burn**
  - burn `Tensor`를 쓰고 `Device`를 가진다.
  - 백엔드는 상관없다. GPU든 CPU(`flex`)든 burn이다.
  - 배치는 전부 여기서 한다.
- **native 배치는 금지한다.** 이걸 허용하면 ndarray가 세 번째 배치 백엔드가 되고, `DiscreteSpace`의 배치 버전 같은 것이 계속 늘어난다.
- "CPU에서만 돈다"는 native의 정의가 아니다. burn도 `flex`로 CPU에서 돌기 때문에 이 기준으로는 둘을 구분할 수 없다.

## 2. 이름과 구조

- `core`에 빈 마커 구조체 `pub struct Native; pub struct Burn;`를 둔다.
- 개념마다 자기만의 매핑 trait을 둔다. 공유 매핑 trait은 모든 개념이 정말 같은 걸 필요로 할 때만 만든다.

  | 개념 | 매핑 trait | Native | Burn |
  |---|---|---|---|
  | 행동 선택 | `ActionSelectorRepr { type Inner }` | `SmallRng` | `()` |
  | 이산 공간 | `DiscreteSpaceRepr { type Inner }` | `SmallRng` | `Device` |
  | 전이 | `TransitionRepr { type Flag; type Extra }` | `bool`, `()` | `Tensor<1, Bool>`, `BatchDict` |

- 구조체는 개념 이름에 마커를 단다: `EpsGreedy<Repr>`, `DiscreteSpace<Repr>`.
- 생성자는 구현마다 다른 이름으로, 별도 impl 블록에 둔다: `X::native(..)`, `X::burn(..)`.
  - 사용자는 "개념을 고르고, 구현을 고른다": `EpsGreedy::native(eps, seed)`.
  - 같은 이름의 inherent 생성자를 impl 블록마다 두면 E0034가 나서 이름을 나눴다.
- 구현이 하나뿐인 개념은 PhantomData 마커만 둔다.
- 마커 이름은 `Native`/`Burn`을 유지한다. `Single`/`Vector`로 바꾸지 않는다.
  - Space와 행동 선택기에서 마커가 가르는 건 원소 타입이다.
  - 단일/벡터 구분은 `Environment`/`VectorEnvironment`, `Tape`/`VectorTape`의 이름 접두사가 맡는다.
  - 배치라는 사실은 `Batch` 래퍼가 표시한다.

## 3. trait 분리 기준

- 시그니처가 표현마다 다르고, 그 trait을 받는 제네릭 호출자가 있으면 trait을 나눈다.
  - `NativeDiscreteActionSelector` / `BurnDiscreteActionSelector`
  - `NativeDiscreteConstraint` / `BurnDiscreteConstraint`
  - 제약은 trait이 아니라 메서드 수준의 제네릭으로 받는다. 환경들이 `()`와 마스크를 모두 쓰기 때문이다.
- `Environment`는 trait 하나로 둔다.
- trait이 결국 두 벌씩 생기지만, 사용자는 `EpsGreedy::native`처럼 구조체 생성자만 보므로 상관없다.

## 4. 환경 규칙

1. **벡터 환경은 burn으로만 만든다.**
2. **단일 환경은 native로만 만든다.** burn 단일 환경은 금지한다.
   - GPU 환경이나 미분 가능한 환경이 필요하면 `VectorEnvironment`로 직접 구현한다 (n=1도 가능).
   - 환경을 GPU에서 돌려 얻는 이득은 여러 환경을 한 번에 계산하는 데서 나온다. 예를 들어 SHAC(Xu et al., ICLR 2022)는 GPU 미분 가능 시뮬레이터로 병렬 궤적 N=64를 쓴다 (4.3절, 부록 A.2.3 표 5).
3. 단일 `Environment`는 플래그로 항상 `bool`을 내고, device가 없다. 그래서 `Flag` 연관 타입도 두지 않는다.
4. 단일 → 벡터 변환은 `SynchronizedVectorEnvironment`(SyncEnv)가 한다.
   - device는 SyncEnv가 가진다.
   - 이름은 바꾸지 않는다. 변환은 "단일 환경 여러 개를 벡터로 묶는 일"의 일부다. 이름은 실행 방식(동기/비동기)을 나타낸다.
5. **deep은 벡터 환경만 받는다.**

## 5. 공간 (Space)

- `DiscreteSpace`
  - Native: 원소 `usize`, `SmallRng`를 가진다.
  - Burn: 원소 텐서, `Device`를 가진다.
  - 마커 방식을 그대로 유지한다.
- `ContinuousSpace`도 마커를 단다.
  - Native: shape는 `[usize; D]`, 원소와 bounds는 `ArrayD<f32>`, device가 없다.
  - Burn: `Tensor<D>`, `Device`.
- native에 ndarray를 쓰는 이유:
  - 이미 의존성에 있다 (`ndarray = "0.17.2"`).
  - numpy 0.29와 같은 ndarray 버전이라 gym 값을 그대로 받을 수 있다.
  - `Vec<f32>`와 달리 shape이 보존된다.
- `ArrayD`를 고른 이유: ndarray의 `Dimension`은 N마다 따로 구현되어 있어서, const 제네릭 D로 `Array<f32, Dim<[Ix; D]>>`를 쓰면 바운드가 붙는다.
- 예전 `crates/rl/env/src/space/continuous.rs`가 같은 설계라 참고한다.
- ndarray는 단일 값 표현에만 쓰고 배치 축은 담지 않는다.

## 6. 변환 경계

- 변환은 **환경 출력에서만** 일어난다. Transition 자체를 변환하는 일은 없다.
- 시그니처는 원소 하나 단위가 아니라 `Vec` 단위로 둔다. 텐서 생성과 전송을 한 번으로 모으기 위해서다.

  | 대상 | 방식 | 방향 |
  |---|---|---|
  | 관측 | Space 메서드, `Vec<원소>` → burn | native → burn |
  | 행동 | Space 메서드, burn + `n` → `Vec<원소>` (안에서 `into_data` 한 번) | burn → native |
  | 보상, 제약 | 단독 trait의 연관 함수, `Vec<Self>` → burn | native → burn만 |
  | 플래그 | SyncEnv가 `Tensor::from_bool` | native → burn |

- 보상과 제약은 Space가 없으므로 `&self` 없는 연관 함수로 만든다.
  - 길이는 `Vec`에서 나온다. 그래서 `()`도 문제가 없다.
  - 환경으로 되돌아가지 않으므로 방향은 하나만 필요하다.
- 행동의 개수 `n`은 SyncEnv가 안다. `()`는 `vec![(); n]`으로 만든다.
- 근거: 측정 결과 (burn 0.23.0-pre.1, `flex` CPU, 2코어, 반복 2000회 평균).

  | N | 관측: 원소별 텐서 + `cat` | 관측: 텐서 한 번 | 행동: 원소별 `into_scalar` | 행동: `into_data` 한 번 |
  |---|---|---|---|---|
  | 8 | 3.3 µs | 0.4 µs | 5.6–6.8 µs | 0.2–0.3 µs |
  | 64 | 22–30 µs | 0.9–1.0 µs | 41–44 µs | 0.3 µs |
  | 256 | 94–96 µs | 2.1 µs | 166–177 µs | 0.7 µs |

  GPU에서는 원소별 방식이 host↔device 전송과 동기화를 N번 일으킨다. 아직 측정하지 않았다.

## 7. Tape와 Transition

- `Tape<E: Environment>`: 단일 native 환경을 받고 `Transition<Native, ..>`를 낸다. tabular와 온라인 linear가 쓴다.
- `VectorTape<E: VectorEnvironment>`: `Batch<Transition<Burn, ..>>`를 낸다. deep이 쓴다.
- `Transition`은 `TransitionRepr`를 유지한다.
  - 단일 Tape는 native만, VectorTape는 burn만 내므로 이름과 실제가 일치한다.
  - 그래서 Flag/Extra를 제네릭으로 풀 필요가 없다.
- BatchOps derive는 필드 타입마다 where 절을 붙인다. 그래서 `Transition<Native>`에는 BatchOps가 자동으로 붙지 않고, burn 쪽에만 붙는다.

## 8. linear

- 온라인 (단일 환경, 한 step씩): native.
- 배치 (여러 환경, 미니배치): burn. native 환경 N개를 SyncEnv로 묶어 쓴다.

## 9. gymnasium

- gym 모듈은 일단 꺼둔다.
- 다시 켤 때 deep용 gym은 벡터 환경으로 만든다.
  - 먼저: 단일 gym 환경을 native(`ArrayD<f32>`)로 받고, SyncEnv로 감싼다. tabular용으로도 그대로 쓸 수 있다.
  - 필요하면 나중에: gymnasium 벡터 환경을 `VectorEnvironment`로 직접 구현한다.
    - autoreset은 `DISABLED`로 두고, `reset(options={"reset_mask": ...})`를 `VectorTape`의 마스크 리셋에 연결한다.
    - 기본값인 `NEXT_STEP`은 가짜 리셋 전이를 낸다. 참고: https://gymnasium.farama.org/main/api/vector/autoreset/

## 10. 버퍼

- 사용처가 deep뿐이라 `core`에서 `deep`으로 옮긴다.
- Buffer = Storage + Sampler.
  - 생성자: `Buffer::replay`, `Buffer::prioritized_replay`, `Buffer::rollout`, `Buffer::episode`.
  - 별칭: `ReplayBuffer<T>` 등. `T: BatchOps` 제네릭 하나만 둔다.
- Ring 저장소는 time-major `[capacity_steps, N]`로 둔다. 이러면 용량을 N으로 나눠떨어지게 맞출 필요가 없다.
- Rollout은 샘플러 없이 통째로 꺼내고 비운다 (drain).
- Episode는 늘어나는 저장소로 둔다. 예전 RolloutBuffer의 쌓기 방식을 재사용한다.
- Sampler는 인덱스와 가중치를 돌려준다.
- 샘플 정보(`is_weights`, `indices: Tensor<1, Int>`)는 샘플된 Batch의 `BatchDict`에 typed `Key<T>` 상수로 넣는다. 그래서 알고리즘 시그니처에 `SampleInfo`가 따로 없다.
- n-step 윈도우는 저장소가 만든다. 할인과 off-policy importance sampling은 알고리즘 쪽에서 한다.
- sum tree와 PER은 논문을 보고 직접 다시 구현한다. v5의 `prioritized.rs`를 검증용 기준으로 남긴다.

## 미정

- Space trait을 `NativeSpace`/`BurnSpace`로 나눌지.
  - 나누면 변환 메서드를 `NativeSpace`에 넣을 수 있다.
  - 공통 상위 trait을 남길지도 같이 정해야 한다.
- Space의 `sample` RNG 설계.
  - 지금 `sample(&mut self)`는 `action_space(&self)`와 충돌한다.
  - Space를 Clone하면 RNG가 복제되고, MaskedCliffWalking에서는 관측과 행동 공간이 같은 시드를 쓴다.
- 단일 `Tape`에 "native 원소" 바운드를 걸어서 burn 원소를 컴파일 단계에서 막을지.
- 변환 시 `to_device`를 붙일지.
- Python GPU 복사를 실제로 통합하는 문제 (`torch.txt` 참고): device 분기, 스트림 동기화, N차원, 역방향, dtype.
