# single / batched data (35-refactor)

revised version of 20261107 (had a conversation with Claude, and made some decisions. written by claude)

## Summary

- Types are named by **the shape of the data they take or return**.
    - takes or returns non-batched data → **no prefix** (`EpsilonGreedy`, `DiscreteSpace`, `Environment`, `Transition`)
    - takes or returns batched data → **prefix `Batched`** (`BatchedEpsilonGreedy`, `BatchedDiscreteSpace`, `BatchedTransition`)
- The implementation tool (std / `ndarray` / `burn`) never appears in public names.
    - In practice, single types are implemented with std types and `ndarray`, and batched types are implemented with `burn`. This is an implementation detail.
- Single environments produce single data. Vectorized environments produce batched data. They are connected only by `SynchronizedVectorEnvironment`.

## Background

During this refactor I also tried two other approaches:
- marker structs `Native` / `Burn` with per-concept mapping traits (`ActionSelectorRepr { type Inner }`, ...)
- a single trait generic over the input type

Both were dropped:
- The markers named the *implementation tool*, so the meaning of the boundary was unclear. Two vocabularies (Native/Burn and Single/Vector) were pointing at the same line.
- The input-generic trait put generics back on every trait bound. This is the same problem as v4.

The final split looks similar to the old crate split (`bake-tabular` / `bake-deep`). The difference is that the line now has a single criterion, the data shape, and a defined way to cross it (section 6).

## 1. three axes, three places

| axis | values | where it appears |
|---|---|---|
| data shape | single / batched | type names (prefix) |
| implementation tool | std, `ndarray` / `burn` | nowhere public; follows from the data shape |
| environment count | 1..N | runtime setting: `SynchronizedVectorEnvironment`'s `n` |
| update scheme | online / from a buffer | the algorithm (which loop calls it) |

- "batched" means **the value has a batch axis**. The algorithm decides what that axis means.
    - vector env step: `[N]`
    - replay minibatch: `[B]`
    - rollout: `[T, N]`
- **no batching for single types.** A single value is exactly one value of one environment at one step.
    - Allowing this would create a third representation, e.g. an `ndarray` batched `DiscreteSpace`.
- "single" is not "CPU only". `burn` also runs on CPU (`flex`), so CPU vs GPU cannot be the criterion.

## 2. naming

- One rule only: no prefix = single, `Batched` prefix = batched.
- There are no marker generics. Each concept has two separate structs, defined in the same file. Shared logic (e.g. the epsilon range check) is a private function in that file.

  | single | batched |
  |---|---|
  | `EpsilonGreedy`, `Boltzmann`, `Greedy` | `BatchedEpsilonGreedy`, `BatchedBoltzmann`, `BatchedGreedy` |
  | `DiscreteSpace`, `ContinuousSpace<D>`, `ByteSpace<D>` | `BatchedDiscreteSpace`, `BatchedContinuousSpace<D>`, `BatchedByteSpace<D>` |
  | `Space` | `BatchedSpace` |
  | `DiscreteActionSelector`, `DiscreteConstraint` | `BatchedDiscreteActionSelector`, `BatchedDiscreteConstraint` |
  | `Environment`, `Tape` | `BatchedEnvironment`, `BatchedTape` (still `VectorEnvironment`, `VectorTape` in code) |
  | `Transition` | `BatchedTransition` |
  | – | `BatchedDict` |
  | `core::env::wrapper::X` | `core::env::wrapper::vec::X` (same wrapper name) |

- Environments and tapes are named by their **interface**, not by how many environments run inside.
    - A single environment used with deep RL is "a batched environment of size 1", made by `SynchronizedVectorEnvironment` with `n = 1`.
    - A neural network needs `[1, obs]` tensors anyway, so this per-step conversion is required regardless of the environment count.
- Considered: same names in sibling modules (`single::EpsilonGreedy` / `batched::EpsilonGreedy`).
    - pros: short names in code that uses only one side, symmetric, easy to browse per module in rustdoc
    - cons: boundary code (`SynchronizedVectorEnvironment`, conversion, tapes, buffers, linear with both implementations, equivalence tests) needs paths or `as` everywhere, and names are not unique in grep or error messages
    - Chose the prefix because bake has a lot of boundary code. Revisit if most user code ends up using only one side. It is a mechanical rename.

## 3. traits

- Split a trait into a single and a batched version when the signatures differ and generic callers exist.
    - `Space` / `BatchedSpace`: different `sample` signatures
    - `DiscreteActionSelector` / `BatchedDiscreteActionSelector`: different constraint bounds
    - `DiscreteConstraint` / `BatchedDiscreteConstraint`: these cannot be one trait with an associated type, since `()` must be usable on both sides
- A single trait generic over the input type (`SelectAction<Q>`) also works: tested, and the argument type picks the impl. Rejected because it puts generics back on every bound.
    - Two traits with the same method name are ambiguous when both are in scope (`E0034`), even if the argument types differ.
- Environment bounds:
    - `Environment`: `ObsSpace: Space`, `ActionSpace: Space`
    - `VectorEnvironment`: `ObsSpace: BatchedSpace`, `ActionSpace: BatchedSpace`, `Constraint: BatchOps`, `Reward: BatchOps`

## 4. environments

1. **batched (vector) environments produce only batched data.**
2. **single environments produce only single data.** No single environment with `burn` elements.
    - If a GPU or differentiable environment is needed, implement `VectorEnvironment` directly (`n = 1` is fine).
    - Rationale: GPU simulation pays off by computing many environments at once. For example, SHAC (Xu et al., ICLR 2022) uses a GPU differentiable simulator with N = 64 parallel trajectories (section 4.3, appendix A.2.3, table 5).
3. A single `Environment` always returns `bool` flags and has no device. There is no `Flag` associated type.
4. single → batched conversion is done only by `SynchronizedVectorEnvironment`.
    - bound: `E: Environment<ObsSpace: IntoBatchedSpace, ActionSpace: IntoBatchedSpace, Constraint: IntoBatched, Reward: IntoBatched>`
    - The device lives in this wrapper.
    - The name describes execution (synchronous). Conversion is part of "binding N single environments into one batched environment".
5. **deep RL algorithms take only batched environments.**
6. Single `Tape` has **no autoreset**. Callers check `done()` and call `reset()`.

## 5. spaces

- **Single spaces have no batch axis.** CartPole observation: `[4]`.
    - `ContinuousSpace<D>`: `D` is the rank of one element. Element and bounds are `ArrayD<f32>`. No device.
    - `ByteSpace<D>`: same, with `u8`.
    - `DiscreteSpace`: element `usize`.
- **Batched spaces' first axis is the environment's batch size `N`.** CartPole observation: `[N, 4]`.
    - Batched `sample` needs no `n` argument.
    - Caution: `N` is only the batch size of that environment interface. The same batched data appears with other sizes, e.g. a minibatch `[B]` or a rollout `[T·N]`. Code that also takes minibatches (action selectors, networks) must use only the feature dims (`shape()[1..]`).
- `ContinuousSpace<F>` → `BatchedContinuousSpace<F + 1>`:
    - `{ F + 1 }` with a generic `F` does not compile on stable Rust ("generic parameters may not be used in const operations").
    - Use macro-generated impls per rank instead, e.g. `1 => 2, 2 => 3, 3 => 4, 4 => 5`. Tested.
- Why `ndarray` for single:
    - already a dependency (`ndarray = "0.17.2"`)
    - the same version as numpy 0.29, so gym values come in directly
    - keeps the shape, unlike `Vec<f32>`
- Why `ArrayD`: `ndarray`'s `Dimension` is implemented per N, not for a const generic N. `Array<f32, Dim<[Ix; D]>>` would need extra bounds.
- **RNG:**
    - Single spaces take the RNG from outside: `sample(&self, rng)`, like rand's `Distribution::sample`.
        - With `sample(&mut self)`, the space could not be sampled through `action_space(&self)`.
        - Cloning a space duplicated its RNG, and obs/action spaces shared seed 0 in CliffWalking.
    - Batched spaces use the device RNG.
        - `burn` has only `Device::seed`, no getter (`burn-tensor/src/device.rs`).
        - The state is effectively global (flex: `static SEED: Mutex<Option<StdRng>>`), so results reproduce only when seeding once at start and keeping the order of random ops.

## 6. conversion

- Conversion happens **only at environment outputs**, in `SynchronizedVectorEnvironment`. A `Transition` is never converted.
- Signatures take a whole `Vec`, not one element, to make one tensor and one transfer.

  | object | trait | function | direction |
  |---|---|---|---|
  | obs / action space | `IntoBatchedSpace` | `into_batched(self, device) -> Self::Batched` | single → batched |
  | observation | `IntoBatchedSpace` | `bind(Vec<Element>, device)` | single → batched |
  | action | `IntoBatchedSpace` | `unbind(batched element) -> Vec<Element>` (one `into_data` inside) | batched → single |
  | reward, constraint | `IntoBatched` | `into_batched(Vec<Self>, device)` | single → batched only |
  | flags | `IntoBatched for bool` | `Tensor<1, Bool>` | single → batched |

- `bind` adds the batch axis (`[4]` × N → `[N, 4]`). `unbind` removes it.
- Reward and constraint have no space, so `IntoBatched` is an associated function without `&self`. The length comes from the `Vec`, so `()` works.
    - implemented for: `()`, `bool`, `f32`, `usize`, `[bool; N]`, `Vec<bool>`
- Benchmark (Claude; burn 0.23.0-pre.1, `flex` CPU, 2 cores, mean of 2000 runs):

  | N | obs: per-element tensor + `cat` | obs: one tensor | action: per-element `into_scalar` | action: one `into_data` |
  |---|---|---|---|---|
  | 8 | 3.3 µs | 0.4 µs | 5.6–6.8 µs | 0.2–0.3 µs |
  | 64 | 22–30 µs | 0.9–1.0 µs | 41–44 µs | 0.3 µs |
  | 256 | 94–96 µs | 2.1 µs | 166–177 µs | 0.7 µs |

## 7. data containers and transitions

- `Transition<Obs, Action, Constraint, Reward>`: `bool` flags, no extra. Not `BatchOps`.
- `BatchedTransition<Obs, Action, Constraint, Reward>`: `Tensor<1, Bool>` flags, extra `BatchedDict`. Derives `BatchOps`.
    - The parameter order is the same for both (`Obs, Action, Constraint, Reward`).
- Fields stay `pub`.
    - The batched side is already read-only through the container (`Deref` only, no `DerefMut`). Changes go through container methods (`insert`).
    - Getters returning `&Tensor` would force clones. A live clone makes later in-place ops copy (CoW).
    - SB3 (`NamedTuple`), Tianshou (`Batch` attributes) and TorchRL (keys) also expose fields directly.
- Container `Batch<T>` → **`Shaped<T>`** (rename pending in code).
    - It only adds the batch shape (`bs`) to batched data. Tensors fold batch dims into the first axis, `dims()[0] == product(bs)`.
    - It stays a public generic, because buffers are generic over `T: BatchOps`.
    - Usage: `Shaped<BatchedTransition<..>>`.
    - Rejected: hiding the leaf behind an alias.
        - A `pub` alias to a `pub(crate)` leaf fails in user crates ("type ... is private").
        - A `pub` leaf inside a private module works, but gives two names for one type, and users cannot construct it.
- `flatten` only changes `bs` (metadata). The flat index of `(t, env)` is `t·N + env`.

## 8. algorithms

- Algorithms are split by the **data shape they take**, not by the update scheme.
    - single implementation: takes single values, updates per step (tabular, online linear with one environment)
    - batched implementation: takes batched data. Covers both online updates with N environments (`[N]`) and updates from buffers (`[B]`, `[T, N]`).
- Most algorithms need only one side (tabular: single, DQN/PPO: batched). Linear methods need both.
- When both exist, add a test: the batched implementation with batch size 1 must equal the single implementation.
- In RL literature, "batch updating" means updating from collected experience (Sutton & Barto 6.3). That is the update-scheme axis, not the data-shape axis.

## 9. buffers (`deep::buffer`)

Structure follows TorchRL's Storage / Writer / Sampler split:

| TorchRL | bake |
|---|---|
| Storage | `Shaped<T>` held by the buffer |
| Writer | `RingWriter` (wrap) / `LinearWriter` (fill once, panic on overflow) |
| Sampler | `Sampler` (replay) / `EpochSampler` (rollout) |

- Writers compute positions only. They hold no data.
- The buffer pairs the data and the writer state as private fields, and resets both together in `init` / `clear`.
- The writer asserts that the storage length equals its capacity.

### replay buffer

- Pre-allocated, time-major `[rows, N]`, with `rows = ceil(C / N)`, like Tianshou (`vecbuf.py`) and TorchRL `ndim=2`.
    - Each push writes exactly one row, so writes never split at the wrap.
    - The actual capacity is `rows × N` (at most `N − 1` more than requested).
    - Push size `N` must be the same for every push.
- `sample(size)` flattens the storage and draws flat indices from `0..len·N`.
- API: `push`, `len`, `sample`, `clear`.

### sample info

- `Sample { sample, indices, info: S::SampleInfo }`: typed per sampler, returned separately from the data. Tianshou returns `(batch, indices)`, and flashbax PER returns `indices` and `probabilities` as fields.
    - uniform: `SampleInfo = ()`
    - prioritized: IS weights
- IS weights:
    - **computation** belongs to the sampler (e.g. PER's `(N·P(j))^-β / max w`)
    - **reduction** of a per-sample loss is a shared trait: `()` → plain mean, `Tensor<1>` → weighted. Pick one formula (`mean(x·w)` as in Tianshou, Dopamine and CleanRL, or `Σ(x·w)/Σw` as in TorchRL) and keep it.
    - **where to apply** is the algorithm's choice. DQN has one loss. TorchRL's SAC weights the actor, Q and value losses but not the alpha loss.
- No separate `dqn_per`: the loss is generic over the weight type, so the sampler's `SampleInfo` picks the path at compile time.

### rollout buffer

- No sampler. API: `push`, `is_full`, `pop`.
- PPO: `pop` → insert advantage and return into `extra` → `EpochSampler` (shuffle) yields minibatches for one epoch.
- A2C: use the popped batch directly.
- `pop` moves the storage out, so there is no copy.
- Storage is pre-allocated `[T, N]`.
    - CleanRL PPO does the same (`torch.zeros((num_steps, num_envs, ..)).to(device)`). SB3 also pre-allocates, but re-allocates on every `reset`.
    - TorchRL's collector appends to a list per step, then `torch.stack(.., out=...)` into a pre-allocated output.
    - CPU measurement (native CartPole, rollout 512):
        - pre-allocated push costs ~11–13 µs per step, independent of N
        - Vec + one `stack` at pop was ~15% faster overall with N = 1, and within noise with N = 16
    - GPU reasoning (not measured):
        - `burn`'s default `cat` is one `slice_assign` per input (`burn-backend` `cat_with_slice_assign`), and `burn-cubecl` does not override `float_cat`. So Vec + stack does not reduce kernel launches on GPU, it only moves them to `pop`.
        - Pre-allocated writes spread over steps and can overlap with CPU env stepping.
    - Kept pre-allocated. Re-check on GPU with the benchmarks.

### REINFORCE (exact)

- Sutton & Barto 13.3 (episodic): generate one full episode with the current θ, then update with `γ^t G_t ∇ln π`.
- With N environments: fix θ, run until **every environment finishes one episode**, mask steps after each environment's first `done`, then update.
    - N = 1 equals the textbook algorithm.
    - N > 1 is the k-sample REINFORCE of RLOO (Ahmadian et al. 2024, 2.3) and Kool et al. (2020, 3.3).
- Loss: `−(1/N) Σ_i Σ_t γ^t G_t ∇ln π`. Sum over time, mean over episodes. Not a mean over all steps.
- The length is unknown in advance, so this uses Vec accumulation + one `stack`. This is the one case where Vec storage fits.
- Requires a time limit or a max step count.
    - Truncated episodes are dropped by default, so only exact returns remain.
    - If nothing remains, skip the update and warn.
- `γ^t`: included (as in the pseudocode).
- Per-step θ updates (as in the pseudocode) vs one summed update: summed. Note this difference from the pseudocode.
- `EpisodeBuffer` is dropped. Episode structure (HER, sequence sampling) is handled by samplers or indices over normal storage, like TorchRL's `SliceSampler` and Tianshou's `HERReplayBuffer`.

## 10. performance notes

- PPO CartPole 15 s → 26 s was caused by the **Python environment**, not by bake or `burn`. With the native CartPole it is 15 s again.
- Per step (Claude, 2-core container):
    - Python `step` ~9 µs (wrappers ~2 µs)
    - pyo3 + numpy → `ArrayD` ~3.5–5.5 µs
    - `SynchronizedVectorEnvironment` + tape ~3 µs (also for native)
    - native `step` 0.13 µs
- Use native environments in examples and benchmarks when they exist.
- For gym environments with many copies, a gymnasium vector env as `VectorEnvironment` (one Python call per step) is the next step.

## 11. gymnasium

- A single gym environment is a single environment (`ArrayD<f32>` from numpy). Use it with `SynchronizedVectorEnvironment` for deep RL, or directly for tabular.
- Later: gymnasium vector env as `VectorEnvironment`.
    - Set autoreset to `DISABLED` and connect `reset(options={"reset_mask": ...})` to the tape's reset mask.
    - The default `NEXT_STEP` mode returns a fake reset transition. See https://gymnasium.farama.org/main/api/vector/autoreset/

## 12. documentation note

- An impl method without a doc comment inherits the trait's doc. With its own doc, the trait's doc is replaced.
- To keep the trait's doc and add to it, put the text in a `macro_rules!` and use `#[doc = text!()]` on both the trait and the impl, then add `///` lines after it.
